# Тендерный фильтр — ИИ-скоринг закупок (кейс-чемпионат AI Procurement Copilot, задача 4)

[![CI](https://github.com/Aludra568/TenderFilter/actions/workflows/ci.yml/badge.svg)](https://github.com/Aludra568/TenderFilter/actions/workflows/ci.yml)

Поставщик загружает извещение из ЕИС (44-ФЗ или 223-ФЗ), указывает ИНН своей компании и описывает
критерии обычным текстом — за доли секунды получает оценку 0–100 %, вердикт
«Участвовать / Рассмотреть / Не участвовать» и объяснение каждого балла
со ссылкой на поле извещения.

**Главный принцип: понимаем и считаем без чёрного ящика, нейросеть — вторая линия.** Текст критериев
разбирает экспертная система (словарная морфология pymorphy3, грамматики yargy, справочники), числа
оцениваются нечёткой логикой, веса задаются ранжированием или методом анализа иерархий. Нейросеть
(если подключена) доразбирает нестандартные фразы и перепроверяет готовую оценку, автоматически
корректируя вердикт по подтверждённым цитатам. Поэтому оценка воспроизводима, объяснима,
укладывается в лимит 10 секунд и проверяема на эталонном наборе.

## Быстрый старт

```bash
docker compose up --build
```

| Что | Адрес |
| --- | --- |
| Интерфейс | http://localhost:8080 |
| API + Swagger | http://localhost:8000/docs |

При первом запуске база заполняется демо-данными: 37 извещений (36 в структуре реальных выгрузок ЕИС
со сроками «от сегодня» + одно настоящее извещение из ЕИС) и профиль IT-поставщика из Новосибирска.

Внешние ключи не нужны. ЕГРЮЛ по любому ИНН берётся из открытых сервисов ФНС (egrul.nalog.ru и реестр МСП),
для демо-ИНН — из встроенных данных; с ключом DaData (`EGRUL_PROVIDER=dadata`, `DADATA_API_KEY`) — полный список ОКВЭД.
LLM — локальная модель в Ollama (`qwen2.5:1.5b`, скачивается в фоне; пока её нет, критерии разбираются правилами).

**Главный сценарий из ТЗ — страница «Оценить»** (http://localhost:8080/quick): файл ЕИС + ИНН + параметры текстом →
оценка, рекомендация, обоснование и время каждого этапа. Кнопки «Взять реальное извещение» и «Пример формулировки»
позволяют проверить всё за 10 секунд.

Требования: Docker с Compose v2, ~4 ГБ свободной памяти (с Ollama), ~3 ГБ места.
Без LLM: `LLM_PROVIDER=none docker compose up --build backend worker frontend`.

## Как это работает

```
Извещение ЕИС (XML/JSON) ─► Парсер → каноническая модель ─┐
ИНН компании и заказчика ─► ЕГРЮЛ (DaData / демо), кэш 24 ч ├─► Движок скоринга ─► оценка, вердикт, объяснение
Критерии текстом ─────────► правила + LLM → настройки ──────┘   (7 факторов, стоп-факторы, без LLM, < 1 мс)
```

**Парсер ЕИС** (`backend/app/eis`). Пути к полям лежат в `field_map.yaml`, поиск идёт по локальным именам
элементов, поэтому новая версия схемы — это правка конфига, а не кода. Структура 44-ФЗ
(`epNotificationEF2020`, `schemeVersion 16.2`) сверена с реальными извещениями из ЕИС:
один из них лежит в `backend/samples/` и используется в тестах. Для каждого поля сохраняется
XPath-путь и исходный фрагмент — это и есть «обоснование ссылками на параметры».
Защита от XXE, лимит 100 МБ, понятные ошибки на битые файлы.

**ЕГРЮЛ** (`backend/app/egrul`). Проверка контрольной суммы ИНН до запроса, цепочка источников
DaData (если есть ключ) → демо-данные → открытые сервисы ФНС без ключа (наименование, ОГРН, статус, регион,
категория МСП и основной ОКВЭД из реестра МСП), кэш в БД на 24 часа. Проверяется и компания пользователя (статус, МСП, ОКВЭД),
и заказчик из извещения (ликвидация, банкротство). egrul.nalog.ru при частых запросах просит капчу и временно
блокирует IP, поэтому перед ФНС стоит размыкатель: после капчи, 403/429 или таймаута сервис не опрашивается
60 с → 120 с → … до 15 мин, а пакет сразу идёт на кэш (состояние — в `GET /api/health`, поле `fns_breaker`).

**Загрузка по номеру из ЕИС** (`backend/app/eis/getdocs.py`). Открытый FTP ЕИС закрыт с 01.01.2025, поэтому
есть адаптер официального сервиса getDocsIP: `POST /api/tenders/by-number` с реестровым номером 44-ФЗ.
Нужен токен физлица из личного кабинета ЕИС (`EIS_TOKEN`); без него загрузка — файлами.
Адаптер покрыт тестами на сборку запроса и разбор ответа, но с настоящим токеном не проверялся.

**Движок скоринга** (`backend/app/scoring`). Семь факторов — они же оси «паутинки»:

| Фактор | Базовый вес | Что учитывает |
| --- | --- | --- |
| Профильность | 25 | ОКПД 2 закупки ↔ ОКВЭД компании, ключевые слова, смысловая близость (векторы) |
| Цена | 15 | НМЦК в рабочем диапазоне |
| География | 15 | Свои регионы, соседние в том же федеральном округе, исключённые |
| Сроки | 15 | Дни до окончания подачи, срок исполнения контракта |
| Финансы | 10 | Обеспечения заявки и контракта против лимита, аванс |
| Условия участия | 15 | Закон, способ закупки, только СМП, национальный режим |
| Заказчик | 5 | Статус и возраст по ЕГРЮЛ |

Оценка = взвешенная сумма факторов, по которым есть данные; отдельно считается полнота данных. Решение всегда автоматическое: если в извещении меньше 70% данных, вердикт считается по найденному, но не выше «Рассмотреть», с пометкой, каких данных не хватило.
Стоп-факторы (срок истёк, закупка только для СМП при не-МСП, исключённый регион или способ,
«обязательные» условия) дают «Не участвовать». Красные флаги (ключевой фактор на нуле,
ликвидирующийся заказчик) ограничивают вердикт «Рассмотреть». Важность каждого фактора (0–5),
пороги и «обязательность» настраиваются; есть произвольные правила по любому полю
(`custom_rules`) — всё без изменения кода.

**Мастер весов** (страница «Профиль», `POST /api/weights`). Два способа вместо ползунков:
расставить факторы по порядку (веса Rank Order Centroid: 37 %, 23 %, 16 %, 11 %, 7 %, 4 %, 2 %) или ответить
на 10 попарных вопросов «что важнее и во сколько раз» (метод анализа иерархий Саати, неполная матрица,
логарифмические наименьшие квадраты). При противоречивых ответах (CR > 0,1) веса всё равно считаются,
а система показывает, какой ответ спорит с остальными и какое значение из них следует.

**Критерии текстом** (`backend/app/nlp`). Правила на регулярных выражениях и справочнике 89 регионов
понимают типовые фразы («НМЦК от 1 до 30 млн», «в Алтайском крае — если выгодно»,
«конкурсы не берём», «аванс обязателен», «кроме Тывы»). То, что правила не поняли, отправляется
в LLM со строгой JSON-схемой. LLM ждём не дольше 5 секунд (`LLM_PARSE_TIMEOUT_SECONDS`): не успела —
остаётся результат правил, так что вся цепочка укладывается в 10 секунд из ТЗ. Каждое правило помнит
фразу-источник, непонятые фразы показываются пользователю.

**Документы закупки** (`backend/app/docs`). К извещению можно приложить проект контракта и ТЗ (.docx, .pdf с текстом,
.txt). Правила находят срок оплаты и приёмки, аванс (его нет в XML ЕИС), пени и штрафы, гарантийный срок,
товарные знаки без «или эквивалент» и требование «только оригинал». Каждая находка помечена стороной,
которой она важна, с цитатой из документа и нормой закона (ч. 13.1 и ч. 7 ст. 34, ст. 94, ст. 33 44-ФЗ,
ПП № 1042). Для поставщика риски снижают фактор «Условия участия», кассовый разрыв учитывается в «Финансах».

**Защита обеих сторон.** Поставщику — риски контракта, склады и филиалы в профиле («есть склад в Красноярске»)
и динамический лимит обеспечений: отметки «готовим / подали / выиграли» замораживают деньги, и свободный лимит
для остальных закупок пересчитывается. Заказчику — страница «Заказчику» (`POST /api/customer/check`): срок подачи
против минимумов ст. 48–50 44-ФЗ, условия проекта контракта, марки без эквивалента, прогноз интереса поставщиков
по типовым профилям; проверка участников по ИНН (`POST /api/customer/participants`): статус и возраст по ЕГРЮЛ,
МСП для закупок «только для СМП», профильный ОКВЭД, антидемпинговые меры ст. 37 при снижении цены на 25% и больше.
Данные о платёжной дисциплине заказчика, арбитраже, жалобах в ФАС и РНП требуют реестров ЕИС по токену
или платных API — в системе для них предусмотрены адаптеры, без источника показывается «не проверено».

**Проверка ИИ** (`backend/app/scoring/review.py`). Оценку считает алгоритм; затем нейросеть (если подключена)
перепроверяет разбор по факторам и автоматически корректирует вердикт. Ограничители: процент оценки
не меняется; вердикт сдвигается не больше чем на одну ступень (Участвовать ↔ Рассмотреть ↔ Не участвовать);
каждое замечание должно опираться на дословную цитату из извещения или критериев — цитата проверяется
по исходному тексту, выдуманная отбрасывается; стоп-факторы нейросеть не отменяет; на ответ отводится
остаток бюджета 10 секунд (по умолчанию до 3 с, `LLM_REVIEW_TIMEOUT_SECONDS`). Нет ответа — остаётся вердикт
алгоритма. В карточке закупки проверку можно запустить кнопкой (`POST /api/scores/{id}/review`).

**Журнал событий** (таблица `audit_log` в PostgreSQL): загрузки, оценки с временем по этапам, запросы ЕГРЮЛ
с источником, разбор критериев, сохранение профилей, пакеты, ошибки. `GET /api/logs`, страница «Точность».

**Векторный поиск.** Предмет закупки превращается в вектор (pgvector в PostgreSQL); на нём работают
смысловой поиск в ленте, «похожие закупки» в карточке и сравнение предмета с профилем.
Векторы строятся без скачивания моделей (хэшированные признаки слов и триграмм) — быстро и офлайн.

## Соответствие критериям ТЗ

| Критерий | Как выполнено | Где проверить |
| --- | --- | --- |
| Парсинг ЕИС | 44-ФЗ и 223-ФЗ, XML и JSON, НМЦК, способ, регион, сроки, обеспечения, ОКПД 2, СМП, нацрежим | `tests/test_parser.py`, реальный файл в `samples/` |
| Интеграция ЕГРЮЛ | Любой ИНН без ключа (ФНС), статус, ОГРН, МСП, ОКВЭД, регион; ввод ИНН в интерфейсе | `GET /api/companies/{inn}`, страница «Оценить» |
| Настраиваемость | Текст → правила, панель с ползунками, строится по схеме `GET /api/factors` | страница «Профиль» |
| Время расчёта < 10 с | Скоринг ~0,5 мс; вся цепочка «файл + ИНН + текст» — десятки мс, время этапов на экране | страница «Оценить», `tests/test_quick_and_logs.py` |
| Обоснование | Каждый фактор: значение, причина, баллы, XPath-источник в извещении | карточка закупки |
| Точность ≥ 80 % | 97 % на 32 сценариях, 0 критических ошибок | `make eval`, `eval/golden.yaml` |
| docker-compose up --build | Postgres + pgvector, Redis, API, Celery-воркер, фронтенд, Ollama | `docker-compose.yml` |

## API — примеры

```bash
# Сценарий из ТЗ одним запросом: выгрузка ЕИС + ИНН + параметры текстом
curl -F "file=@backend/samples/real_44fz_ef2020_0173100008726000065.xml" -F "inn=5406123450"      -F "criteria_text=Работаем в Москве. НМЦК до 150 млн. Поставляем ноутбуки." http://localhost:8000/api/quick-score

# Журнал событий
curl "http://localhost:8000/api/logs?limit=20"

# Оценить извещение из файла по настройкам профиля
curl -F "file=@backend/samples/real_44fz_ef2020_0173100008726000065.xml" http://localhost:8000/api/tenders

# Карточка компании по ИНН
curl http://localhost:8000/api/companies/5406123450

# Разобрать текстовые критерии в настройки (без сохранения)
curl -X POST http://localhost:8000/api/profiles/1/parse -H "Content-Type: application/json" \
     -d '{"text": "Работаем только в Томской области. НМЦК до 10 млн. Аванс обязателен."}'

# Лента, отсортированная по оценке, только «Участвовать»
curl "http://localhost:8000/api/feed?verdict=go"

# Пакет: ZIP с извещениями → обработка в очереди → прогресс
curl -o demo.zip http://localhost:8000/api/demo/batch.zip
curl -F "files=@demo.zip" http://localhost:8000/api/batches
curl http://localhost:8000/api/batches/1

# Выгрузка ленты в Excel
curl -o feed.xlsx "http://localhost:8000/api/feed/export?format=xlsx"
```

## Проверка на реальных извещениях ЕИС

`python -m app.corpus download` собирает свежие извещения 44-ФЗ из поиска ЕИС (публичная печатная форма,
TLS проверяется по официальному сертификату Минцифры), `python -m app.corpus report` меряет полноту разбора.
На 198 реальных извещениях четырёх типов (запрос котировок EZK2020, аукцион EF2020, конкурс EOK2020, EZT2020):
разобрано 198 из 198, предмет, НМЦК, срок подачи, регион и ИНН заказчика найдены в 100% случаев.
Обеспечение заявки найдено в 53–94% — в остальных извещениях его действительно нет (для котировок и
небольших аукционов оно не требуется). Отчёт — `eval/corpus_report.json`, по образцу каждого типа лежит в `samples/`.

Проекты контрактов: `python -m app.corpus contracts` скачивает вложения «Проект контракта» из этих извещений
(46% — .docx, 34% — .pdf, 11% — .doc, 7% — .zip; все форматы поддерживаются), `contracts-report` — что найдено.
На 40 реальных контрактах: читаются 39 (один — скан без текста), пени найдены в 100%, срок оплаты — в 74%,
срок приёмки — в 69%. Проверка на реальных файлах нашла и убрала ложные срабатывания (срок расчётов
с субподрядчиком, требования совместимости с Windows, «оригинальная выписка из банка») — они закреплены тестами.

Загрузка по номеру: поле «номер закупки» на страницах «Оценить» и «Заказчику» и `POST /api/tenders/by-number`
работают без токена через печатную форму ЕИС; при наличии `EIS_TOKEN` резервом служит API getDocsIP.

Классификатор ОКПД 2 по тексту (`app/reference/okpd_model.py`: TF-IDF → LSA → ближайшие соседи) обучен
на 1252 позициях реальных извещений; при проверке с разбиением по извещениям угадывает раздел в 22% (top-3 — 42%):
данных мало и они перекошены. В оценку он не подключён: в 44-ФЗ коды ОКПД 2 есть во всех 198 извещениях корпуса.
Задел для 223-ФЗ и закупок без кодов; отчёт — `eval/okpd_report.json`.

## Скорость

`python -m app.loadtest 1000` — 1000 извещений: разбор XML ЕИС и оценка по профилю на одном ядре
за 3,9 с (≈260 извещений в секунду); разбор XML — медиана 2,7 мс, оценка — медиана 1,0 мс, p95 1,5 мс.
Самое долгое в быстрой оценке — запросы к ФНС (бюджет 3,5 с на организацию, затем кэш на 24 ч).

## Точность разбора критериев

`python -m app.benchmark` — фразы, как их пишут тендерные специалисты, с ожидаемыми настройками,
проставленными вручную (`eval/phrases.yaml`). Правила дорабатывались на этом наборе: 50/50 фраз.
Честная цифра — отложенный набор `eval/phrases_holdout.yaml`, написанный после доработки и для неё
не используемый: 25 из 30 фраз (83%), 89% отдельных проверок, ~3 мс на фразу без нейросети.
Режимы `--mode hybrid` и `--mode llm` дают ту же таблицу для правил с LLM и для одной LLM.

## Что проверено и что нет

- Бэкенд: 148 автотестов (включая 45 проверок «битых» файлов: мусор, обрезанный XML, XML-бомба, XXE, cp1251), эталонный набор, ручной прогон API и интерфейса,
  живой запрос к сервисам ФНС по реальным ИНН.
- Структура XML 44-ФЗ сверена с реальными извещениями ЕИС (октябрь 2026). Шаблон 223-ФЗ составлен
  по документации и требует сверки с реальными файлами.
- Загрузка по номеру через getDocsIP не проверена с настоящим токеном ЕИС.
