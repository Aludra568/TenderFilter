# Тендерный фильтр — ИИ-скоринг закупок (кейс-чемпионат AI Procurement Copilot, задача 4)

Поставщик загружает извещение из ЕИС (44-ФЗ или 223-ФЗ), указывает ИНН своей компании и описывает
критерии обычным текстом — за доли секунды получает оценку 0–100 %, вердикт
«Участвовать / Рассмотреть / Не участвовать / Проверить вручную» и объяснение каждого балла
со ссылкой на поле извещения.

**Главный принцип: LLM понимает — детерминированный движок считает.** Языковая модель один раз
переводит текстовые критерии в правила; каждую закупку оценивает обычный код. Поэтому оценка
воспроизводима, объяснима, укладывается в лимит 10 секунд с запасом в тысячи раз и проверяема
на эталонном наборе.

## Быстрый старт

```bash
docker compose up --build
```

| Что | Адрес |
| --- | --- |
| Интерфейс | http://localhost:8080 |
| API + Swagger | http://localhost:8000/docs |

При первом запуске база заполняется демо-данными: 37 извещений (36 в структуре реальных выгрузок ЕИС
со сроками «от сегодня» + одно настоящее извещение из ЕИС) и профиль IT-поставщика из Новосибирска.

Внешние ключи не нужны. По умолчанию ЕГРЮЛ — демо-данные, LLM — локальная модель в Ollama
(`qwen2.5:1.5b`, скачивается в фоне при первом запуске; пока её нет, критерии разбираются правилами).
Реальные данные ЕГРЮЛ: `EGRUL_PROVIDER=dadata` и `DADATA_API_KEY` в `.env` (см. `.env.example`).

Требования: Docker с Compose v2, ~4 ГБ свободной памяти (с Ollama), ~3 ГБ места.
Без LLM: `LLM_PROVIDER=none docker compose up --build backend worker frontend`.

## Как это работает

```
Извещение ЕИС (XML/JSON) ─► Парсер → каноническая модель ─┐
ИНН компании и заказчика ─► ЕГРЮЛ (DaData / демо), кэш 24 ч ├─► Движок скоринга ─► оценка, вердикт, объяснение
Критерии текстом ─────────► правила + LLM → настройки ──────┘   (7 факторов, стоп-факторы, без LLM, < 1 мс)
```

**Парсер ЕИС** (`backend/app/eis`). Пути к полям лежат в `field_map.yaml`, поиск идёт по локальным именам
элементов, поэтому новая версия схемы — это правка конфига, а не кода. Структура 44-ФЗ
(`epNotificationEF2020`, `schemeVersion 16.2`) сверена с реальными извещениями из ЕИС:
один из них лежит в `backend/samples/` и используется в тестах. Для каждого поля сохраняется
XPath-путь и исходный фрагмент — это и есть «обоснование ссылками на параметры».
Защита от XXE, лимит 100 МБ, понятные ошибки на битые файлы.

**ЕГРЮЛ** (`backend/app/egrul`). Проверка контрольной суммы ИНН до запроса, цепочка источников
DaData → демо-данные, кэш в БД на 24 часа. Проверяется и компания пользователя (статус, МСП, ОКВЭД),
и заказчик из извещения (ликвидация, банкротство).

**Движок скоринга** (`backend/app/scoring`). Семь факторов — они же оси «паутинки»:

| Фактор | Базовый вес | Что учитывает |
| --- | --- | --- |
| Профильность | 25 | ОКПД 2 закупки ↔ ОКВЭД компании, ключевые слова, смысловая близость (векторы) |
| Цена | 15 | НМЦК в рабочем диапазоне |
| География | 15 | Свои регионы, соседние в том же федеральном округе, исключённые |
| Сроки | 15 | Дни до окончания подачи, срок исполнения контракта |
| Финансы | 10 | Обеспечения заявки и контракта против лимита, аванс |
| Условия участия | 15 | Закон, способ закупки, только СМП, национальный режим |
| Заказчик | 5 | Статус и возраст по ЕГРЮЛ |

Оценка = взвешенная сумма факторов, по которым есть данные; отдельно считается полнота данных.
Стоп-факторы (срок истёк, закупка только для СМП при не-МСП, исключённый регион или способ,
«обязательные» условия) дают «Не участвовать». Красные флаги (ключевой фактор на нуле,
ликвидирующийся заказчик) ограничивают вердикт «Рассмотреть». Важность каждого фактора (0–5),
пороги и «обязательность» настраиваются; есть произвольные правила по любому полю
(`custom_rules`) — всё без изменения кода.

**Критерии текстом** (`backend/app/nlp`). Правила на регулярных выражениях и справочнике 89 регионов
понимают типовые фразы («НМЦК от 1 до 30 млн», «в Алтайском крае — если выгодно»,
«конкурсы не берём», «аванс обязателен», «кроме Тывы»). То, что правила не поняли, отправляется
в LLM со строгой JSON-схемой. Каждое правило помнит фразу-источник, непонятые фразы показываются
пользователю.

**Векторный поиск.** Предмет закупки превращается в вектор (pgvector в PostgreSQL); на нём работают
смысловой поиск в ленте, «похожие закупки» в карточке и сравнение предмета с профилем.
Векторы строятся без скачивания моделей (хэшированные признаки слов и триграмм) — быстро и офлайн.

## Соответствие критериям ТЗ

| Критерий | Как выполнено | Где проверить |
| --- | --- | --- |
| Парсинг ЕИС | 44-ФЗ и 223-ФЗ, XML и JSON, НМЦК, способ, регион, сроки, обеспечения, ОКПД 2, СМП, нацрежим | `tests/test_parser.py`, реальный файл в `samples/` |
| Интеграция ЕГРЮЛ | Данные организации по ИНН: статус, ОГРН, ОКВЭД, МСП, регион | `GET /api/companies/{inn}` |
| Настраиваемость | Текст → правила, панель с ползунками, строится по схеме `GET /api/factors` | страница «Профиль» |
| Время расчёта < 10 с | ~0,5 мс на закупку, 100 закупок в пакете — секунды | страница «Точность», `tests/test_api.py` |
| Обоснование | Каждый фактор: значение, причина, баллы, XPath-источник в извещении | карточка закупки |
| Точность ≥ 80 % | 97 % на 32 сценариях, 0 критических ошибок | `make eval`, `eval/golden.yaml` |
| docker-compose up --build | Postgres + pgvector, Redis, API, Celery-воркер, фронтенд, Ollama | `docker-compose.yml` |

## API — примеры

```bash
# Оценить извещение из файла (сразу сохраняет и возвращает разбор)
curl -F "file=@backend/samples/real_44fz_ef2020_0173100008726000065.xml" http://localhost:8000/api/tenders

# Карточка компании по ИНН
curl http://localhost:8000/api/companies/5406123450

# Разобрать текстовые критерии в настройки (без сохранения)
curl -X POST http://localhost:8000/api/profiles/1/parse -H "Content-Type: application/json" \
     -d '{"text": "Работаем только в Томской области. НМЦК до 10 млн. Аванс обязателен."}'

# Лента, отсортированная по оценке, только «Участвовать»
curl "http://localhost:8000/api/feed?verdict=go"

# Пакет: ZIP с извещениями → обработка в очереди → прогресс
curl -o demo.zip http://localhost:8000/api/demo/batch.zip
curl -F "files=@demo.zip" http://localhost:8000/api/batches
curl http://localhost:8000/api/batches/1

# Выгрузка ленты в Excel
curl -o feed.xlsx "http://localhost:8000/api/feed/export?format=xlsx"
```

Полный список — в Swagger: http://localhost:8000/docs

## Разработка без Docker

```bash
cd backend && python -m venv .venv && .venv/Scripts/pip install -r requirements-dev.txt   # Windows
uvicorn app.main:app --reload --port 8000        # SQLite, очередь в процессе API
python -m pytest -q                              # 54 теста
python -m app.evaluation                         # отчёт точности → eval/report.json

cd frontend && npm install && npm run dev        # http://localhost:5173, /api проксируется на :8000
```

## Структура

```
backend/app/
  eis/          парсер ЕИС + field_map.yaml
  egrul/        ЕГРЮЛ: DaData, демо-данные, проверка ИНН, кэш
  scoring/      факторы и движок
  nlp/          разбор критериев: правила + LLM (Ollama / OpenAI-совместимый API)
  reference/    справочники: регионы РФ, ОКВЭД ↔ ОКПД 2, векторы текста
  seed/         демо-компании и генератор извещений
  api.py        REST API          worker.py  очередь (Celery / потоки)
backend/eval/   эталонный набор и отчёт точности
backend/tests/  автотесты
frontend/src/   React + TypeScript: лента, карточка с «паутинкой», профиль, загрузка, точность
```

## Что проверено и что нет

- Бэкенд проверен локально на SQLite: 54 автотеста, эталонный набор, ручной прогон API и интерфейса.
- Структура XML 44-ФЗ сверена с реальными извещениями ЕИС (октябрь 2026). Шаблон 223-ФЗ составлен
  по документации и требует сверки с реальными файлами.
- Сборка `docker compose` на машине разработчика не запускалась (Docker не установлен) — перед сдачей
  её нужно прогнать на чистой машине.
- Аванс ЕИС в XML не публикует (он в проекте контракта во вложениях) — система честно помечает это
  в объяснении и не штрафует за неизвестный аванс.
